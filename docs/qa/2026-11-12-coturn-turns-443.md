# coturn TURNS 443 配置说明与验证步骤

日期：2026-11-12（补写于 2026-11-13）
范围：**只出配置说明与验证步骤，不改 Ola-admin 代码**（主计划 Phase 2.2 的约定）。
本文件位于 Ola 仓库，`Ola-admin` 与 `ola-mobile` 未被本轮修改。

企业防火墙常放行 TCP 443 而封 UDP。现有 TURN 只有明文 3478，这类网络下远控会退化或失败。
TURNS（TURN over TLS）走 TCP 443 可以穿过这类限制。

凭证机制是 coturn REST 临时凭证（`--use-auth-secret`）：
`username = <expiry>:<deviceId>`，`credential = base64(HMAC-SHA1(secret, username))`，
由 `issueTURNCredentials()` 生成。**换成 TURNS 不需要改这套凭证逻辑。**

## 关键限制：配置只能做到「二选一」，做不到「同时下发」

因为 `TURNURL` 是单字符串、`urls` 也是单字符串，**纯配置无法让服务端同时下发
`turn:…:3478` 与 `turns:…:443` 两条**。两个可选路径：

### 路径 A（纯配置，本轮可落地）— 把 TURNURL 换成 TURNS

```bash
# Ola-admin/server/deploy/.env
OLA_REMOTE_TURN_URL="turns:turn.example.com:443?transport=tcp"
```

代价：**失去明文 TURN/UDP 回退**。证书失效、443 被占、或客户端不支持 TURNS 时，
远控直接没有中继可用。因此路径 A 只建议在确认 443 与证书稳定后使用。

### 路径 B（推荐，但需改代码，超出本轮范围）— 同时下发两条

新增 `OLA_REMOTE_TURNS_URL` 环境变量，在 `router.go:196` 与 `:715` 之后各追加一条
`iceServers` 条目（复用同一对 username/credential）。约 6 行改动 + 1 个配置字段。
WebRTC 会自行按网络环境择优，明文与 TLS 并存才是企业网络下的稳妥形态。
**本轮未实施**，记录为后续项。

## coturn 侧配置（路径 A / B 都需要）

`Ola-admin/server/deploy/coturn/turnserver.conf` 改为：

```conf
listening-port=3478
tls-listening-port=443
min-port=49160
max-port=49200
fingerprint
realm=ola-remote.local
no-cli
no-dtls
cert=/etc/coturn/tls/fullchain.pem
pkey=/etc/coturn/tls/privkey.pem
```

要点：

- **删掉 `no-tls`**，否则 TLS 监听不会启动。`no-dtls` 可以保留（TURNS over TCP 不需要 DTLS，少开一个端口）。
- `realm` 建议改成真实域名（现为 `ola-remote.local`）。realm 不影响 TLS，但会影响凭证校验时的诊断可读性；**改 realm 会让已下发的旧凭证失效**，需与客户端重新取会话同步。
- 证书必须是**真实可信证书**（Let's Encrypt 即可），且 CN/SAN 覆盖 `OLA_REMOTE_TURN_URL` 里的主机名。自签证书会被 WebRTC 直接拒绝。
- 私钥挂载进容器时注意权限，不要写入仓库。

`docker-compose.yml` 的 coturn 服务追加：

```yaml
    volumes:
      - ./coturn/turnserver.conf:/etc/coturn/turnserver.conf:ro
      - ./coturn/tls:/etc/coturn/tls:ro
    ports:
      - '3478:3478/udp'
      - '3478:3478/tcp'
      - '443:443/tcp'
      - '49160-49200:49160-49200/udp'
```

**先确认宿主机 443 未被占用**（当前 compose 里没有 nginx 服务，但 `deploy/nginx/` 存在，
实际部署可能在宿主机或另一容器上终结 TLS）。若 443 已被占用，两个办法：

1. 用 5349（TURNS 标准端口）替代 443 —— 但企业防火墙未必放行 5349，收益打折；
2. 让宿主机 nginx 以 `stream` 模块把 443 透传给 coturn（**不能用 http 反代**，TURN 不是 HTTP）。

## 验证步骤（按顺序，每步都要留证据）

### 1. TLS 监听与证书链

```bash
openssl s_client -connect turn.example.com:443 -servername turn.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

期望：返回真实证书的 subject/issuer/有效期，且 SAN 覆盖该主机名。
若握手失败，先查 `no-tls` 是否真的删掉、证书路径是否挂载成功。

### 2. 端口可达性（在受限网络里跑才有意义）

```bash
nc -vz turn.example.com 443
nc -vzu turn.example.com 3478
```

期望：443/TCP 通；3478/UDP 在企业网下不通正是要解决的问题。

### 3. 用临时凭证做一次真实 TURN 分配

凭证按 REST 规则生成（与 `issueTURNCredentials()` 同一算法）：

```bash
SECRET="$OLA_REMOTE_TURN_SECRET"
EXPIRY=$(( $(date +%s) + 3600 ))
USER="${EXPIRY}:probe-device"
CRED=$(printf '%s' "$USER" | openssl dgst -sha1 -hmac "$SECRET" -binary | base64)
```

然后用 coturn 自带客户端做 TLS/TCP 分配（`turnutils_uclient` 的具体开关请先
`turnutils_uclient --help` 确认，不同版本略有差异；目标是「TCP + TLS + 443 + 上面的凭证」）：

```bash
docker compose exec coturn turnutils_uclient --help
```

期望：能看到 `ALLOCATE` 成功与 relayed 地址。失败时区分是凭证问题（401）还是 TLS 问题（握手）。

### 4. 浏览器 ICE 候选验证

在 Trickle ICE 页面填入 `turns:turn.example.com:443?transport=tcp` 与第 3 步的
username/credential，点 Gather。

期望：出现 `typ relay` 候选，且其基础地址是 TURN 服务器。只有 `host`/`srflx` 说明中继没生效。

### 5. 真实 Ola 远控端到端（最终判据）

在**封 UDP 的网络**里，用 Ola 桌面作为控制端连接被控端，走完整远控会话：

- 服务端 `/remote` 会话接口返回的 `iceServers` 里含 `turns:` 条目；
- 会话能建立并看到画面，`chrome://webrtc-internals` 里选中的 candidate pair 是 relay；
- 断开重连一次，确认凭证 TTL 内可重复使用。

**这一步不能用 mock 或本机 staging 替代**（补充验收基准的硬规则）。
本轮**未执行**：没有可用的受限网络环境与已部署 TURNS 的服务端。

## 未覆盖 / 需注意的部分

- **本轮没有改任何 Ola-admin 文件**，也没有部署或重启 coturn。以上全部是待执行的说明。
- **路径 B 未实施**：同时下发 `turn:` 与 `turns:` 需要约 6 行服务端改动，超出「只出配置说明」的范围。
- **中继段是否仍需 UDP 未实测**：TURNS 只保护「客户端 ↔ TURN」这一段。
  `49160-49200/udp` 仍按现有配置发布；当两端不都经同一 TURN 时，UDP 可达性仍可能成为瓶颈。
  coturn 有 TCP 中继相关选项，但是否需要开启、开销多大，**必须在第 5 步实测后再决定**，不要凭猜测打开。
- **证书续期未纳入自动化**：Let's Encrypt 续期后需要让 coturn 重新加载证书（重启容器或 SIGHUP），
  否则续期当天远控会中断。部署时应把续期钩子一并接上。
- **改 realm 会使旧凭证失效**，属破坏性变更，需与客户端取会话的时机协调。
- 移动端（`ola-mobile`）是否接受 `turns:` 与自签证书策略**未核实**，Android/iOS 两端都要在第 5 步一并验证。
