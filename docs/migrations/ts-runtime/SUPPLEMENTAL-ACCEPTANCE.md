# Ola 全量 TS 迁移补充收口与验收基准

本文件配合用户提供的《Ola 全量 TS 迁移与体验优化方案——整合离线优先个人／团队工作空间设计》使用。主计划的产品规则和最终完成标准优先。本目录中的日期日志是过程记录；当前进度只以 [验收台账](acceptance-ledger.json)和实际证据判定。

## 基线

- [工作区快照](worktree-baseline.json)记录开始补充收口前的 Git HEAD、全部已有修改与未跟踪路径；源文件记录 SHA-256，生成产物只记录路径和大小。它不包含文件内容或秘密值，不得用它覆盖用户工作区。
- [能力清单](capability-inventory.json)冻结旧 Worker 的 358 条路由与 CodeGraph 的 18 个语言标识。`staged-ts` 只代表静态同名字符串，不能当作能力迁移完成。删除旧源码后也保留这份冻结清单，直到最终验收归档。
- 台账逐条记录原入口、TS 实现、生产调用路径、旧路径清理、契约和端到端证据。18 个语言、P0–P12、真实主站和六个平台分别验收。若一条旧路由拆成多个 TS 接口，在 `tsImplementation` 和证据里注明对应关系。

## 状态和证据

只使用“未开始、实现中、待验收、通过、受外部条件阻塞”。“通过”须有可复核的测试命令与结果、对应源码或产物位置；路由还须完成旧调用路径清除。人工验收记录应包含平台、版本、日期、场景、结果和截图或日志位置。真实主站与六平台原生验收不得用 mock、交叉打包或本机 staging 替代。

运行 `npm run verify:ts-migration-ledger` 检查清单完整性与证据字段；运行 `npm run verify:ts-migration-exit` 执行严格退出门禁。严格门禁在全部迁移完成前预期失败，失败项就是未关闭事项。最终还要在六个平台对安装产物做无 .NET 资产检查，并在未安装 .NET 的干净系统验证开发启动、CLI、桌面、安装和升级。必要的原生库、WASM 和 Go 服务不属于 .NET 清除范围。

解包产物检查命令为 `npm run verify:legacy-artifacts -- <unpacked-app-root>`。每个目标平台须分别保存其输出作为台账的 `noDotnetEvidence`。

## 收口顺序

1. 为各入口建立旧新契约及失败场景，逐域将 Agent、Cron、渠道、团队、子 Agent 和其余业务迁到统一 TS 服务和调度器；每批更新台账。
2. 完成历史库停写、备份、TS 独占写入和隔离恢复；完成 18 语言 CodeGraph 的固定语料对照和同环境性能门禁。稳定退化超过 10% 时停止对应切换。
3. 验收本地离线、个人／团队模型和空间隔离，完成工作台、全部功能页与 Main 浏览器流程的 Electron 端到端及人工测试。
4. 删除全部 .NET 源码、生产回退、启动和发布依赖；以冻结契约替代旧 Worker 测试夹具，复跑全量测试、真实主站联调和六平台签名、安装、升级与启动验证。

只有台账全部标为“通过”、严格退出门禁与主计划 P0–P12 均通过，才可退出原目标。任何外部条件缺失应记为“受外部条件阻塞”，不能改写为完成。
